# 小红书内容 Agent — 实习面试项目说明

> 适用岗位：后端开发实习、AI 应用开发实习、Python 全栈实习
> 难度定位：中高级（理解全部代码需要一定工程能力）

---

## 一、一句话概述

**多智能体协同的小红书内容自动化生产系统**，从「搜索关键词」到「生成可直接发布的笔记图文」全链路 AI 驱动。

---

## 二、项目亮点（面试口播 30 秒版本）

> "我独立开发了一个多智能体内容生产系统，7 个 AI Agent 协同完成小红书笔记的全流程自动化：从搜索爬取竞品笔记、到数据分析、话题生成、文案撰写、质量评审，最终输出可直接发布的图文内容。技术栈是 Python FastAPI + 多智能体协作架构 + LLM 编排，不依赖 LangChain 等框架，自己实现了 AgentLoop 引擎、记忆系统和多维度评审机制。"

## 四、核心技术决策 & 面试考点

### 4.1 为什么不直接用 LangChain？

**面试回答要点：**
> "LangChain 封装太厚，黑盒调试困难，API 频繁变动导致项目不稳定。我选择自己实现 Agent 基类和调度引擎，对 LLM 调用有完全的控制权——可以精细管理 token 消耗、重试策略、JSON 解析容错。这让我的代码更轻量、可维护性更高，也展示了我对 LLM 调用底层机制的理解。"

**技术细节：**
- 自己实现了 `BaseAgent` 抽象类（`core/agent_base.py`），统一管理 LLM 调用、计时、trace 记录
- 自己实现了 `AgentLoopEngine`（`core/agent_loop.py`），支持两阶段循环调度和 Hook 注入
- LLM 调用使用 OpenAI 兼容 SDK，可无缝切换阿里云灵积 / DeepSeek / 其他兼容模型

### 4.2 多 Agent 如何协作？

**面试回答要点：**
> "7 个 Agent 各司其职，通过一个统一的 PipelineState 对象传递上下文。AgentLoop 引擎负责按预设的阶段顺序调度每个 Agent，每个阶段有明确的输入输出契约。Agent 之间不直接通信，而是通过 PipelineState 共享数据——这是一种类似于 Actor 模型的设计，降低了耦合。"

**技术细节：**
- `PipelineState` 是一个 Pydantic 模型，包含 35+ 个字段，是全局共享上下文
- 每个阶段只读写自己负责的字段
- `LoopHooks` 机制支持阶段级别的干预（重试、跳过、回退路由）

### 4.3 如何保证生成内容质量？

**面试回答要点：**
> "我设计了一个双轨道评审系统。规则引擎做硬性检查（禁词、最小长度、格式合规），LLM 评审做软性判断（真实性、平台风格、AI 感）。两个分数按 7:3 加权，总评低于 75 分自动触发重写，最多重试 3 次。"

**技术细节：**
- `EvaluationEngine`：7 个维度的规则评分（Hook 25%、关键词 15%、真实感 20%、格式 15%、CTA 10%、趋势 10%、受众 5%）
- `LLMJudge`：调用 LLM 做主观评审，检测 AI 模板化痕迹
- `ReflectionEngine`：阈值 + 最大重试次数的重试控制器
- 评审结果写入 `PatternFeedback`，跨会话积累写作经验

### 4.4 记忆系统怎么做的？

**面试回答要点：**
> "实现了一个带压缩的对话记忆系统。每轮对话通过 LLM 生成摘要 + 关键词索引，超过 14 轮或 18000 token 触发压缩合并。同时支持跨会话检索——通过 embedding + TF-IDF + Jaccard 三重相似度打分，从历史对话中召回相关上下文。"

**技术细节：**
- `ConversationManager`：管理写入、摘要、检索全流程
- `CrossSessionRetriever`：三层语义匹配（embedding → TF-IDF → Jaccard）
- `PatternFeedbackStore`：跨会话积累写作规则（如「连续 3 次 Hook 评分低就强化开头提醒」）
- 存储基于 JSON 文件（生产可迁移到 PostgreSQL + pgvector）

### 4.5 爬虫怎么实现的？

**面试回答要点：**
> "用 Playwright 控制真实浏览器访问小红书搜索页面，通过 JS 注入批量提取搜索结果卡片，然后并发打开详情页获取完整内容。处理了登录态持久化、弹窗关闭、反爬对抗等实际工程问题。"

**技术细节：**
- 两阶段爬取：Phase 1 批量提取摘要（快）→ Phase 2 并发提取详情（限 2 个并发）
- 登录状态持久化到 `data/raw/xhs_state.json`
- 爬取结果经过规则过滤（去广告、去视频、去低互动）→ LLM 精筛（质量评分）
- 关键词并行搜索（最多 2 个并发）

## 七、面试高频问题预答

### Q1：这个项目最大的技术难点是什么？

> "多 Agent 协作的状态管理。7 个 Agent 按顺序执行，每个 Agent 只读写 PipelineState 中自己负责的字段，但后续 Agent 依赖前面 Agent 的输出——比如写手器依赖分析器的关键词提取，评审器依赖写手器的完整内容。我设计了一套严格的阶段输入输出校验，确保每个阶段在启动前检查前置数据是否就绪，缺失则提前失败而非跑到一半崩溃。"

### Q2：你写的 Agent 和 LangChain 的 Agent 有什么区别？

> "LangChain 的 Agent 本质是 ReAct 模式——让 LLM 自己决定调用什么工具、什么时候停。这种模式灵活但不可控，token 消耗大。我的 Agent 是确定性流水线——每个 Agent 的职责、输入、输出都是预定义的，LLM 只用在需要创造力的环节（规划、写作、评审），规则能做的绝不用 LLM。这大幅降低了成本和不确定性。"

### Q3：如何保证 LLM 输出的稳定性和格式正确？

> "第一层是 Prompt 设计——每个 Prompt 都要求 JSON 格式输出，并有详细的字段说明。第二层是代码层防御——`chat_json()` 方法会自动检测 JSON 解析失败，带上错误信息让 LLM 重试。第三层是业务校验——解析后的数据会通过 Pydantic 校验，不符合 Schema 的触发降级逻辑或规则补全。"

### Q4：为什么有 legacy_app 目录？

> "这是一个渐进式重构项目。legacy_app 是原始版本——它能跑，但架构耦合度高、依赖 LangChain。我在不破坏原有功能的前提下，逐步把核心逻辑迁移到新架构，同时新架构可以直接复用 legacy_app 的爬虫和飞书服务。这模拟了真实工作中「在飞行中换引擎」的场景。"

### Q5：如果要把这个项目上线，还需要做什么？

> "- 把 JSON 文件存储换成 PostgreSQL + pgvector
- 发布模块接入小红书真实 API（需要申请开放平台权限）
- 增加账号授权系统（OAuth + Session 管理）
- 添加请求队列和并发限制（Celery + Redis）
- 前端从原生 HTML 升级到 React/Vue + 状态管理
- 添加日志监控和告警系统"
